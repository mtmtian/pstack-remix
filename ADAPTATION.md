## Maintained source

The repository `mtmtian/pstack-remix` is maintained as one checkout per machine for both hosts. `.codex-plugin/plugin.json` preserves the installed Codex name; `.claude-plugin/plugin.json` exposes the Claude name `pstack`. The repository includes native marketplace manifests for both hosts, named `pstack-local`. Existing Codex `personal` registrations may keep pointing at the same checkout. Both consume the same 58 skills, 23 playbooks, 2 agent files, and runtime helpers. Host caches are generated installation artifacts, never edit targets.

Shared preferences live at `~/.config/pstack/config.json`. `bin/config.mjs` supplies read-only resolution, idempotent initialization/legacy import, host-scoped updates, null-to-remove overrides, validation, locking, and atomic writes. A concrete model ID cannot be stored in the common policy. An `xagent:<agent>` entry can, because `bin/xagent` dispatches it to the named local agent CLI the same way from either host; so can `xagent:<agent>/<model>`, whose model goes only to that CLI's own model flag. `bin/xagent --effort` maps the worker's effort to each CLI's own effort flag, and the receipt records the requested model and effort. The `xagent` skill, its allowlist, and the pi guard are local additions with no upstream counterpart; `scripts/xagent-e2e.sh` is their behavioral test. Replays in `create-verification-skill` and `maintain-verification-skill` are also local additions, adapted from tester.army `e2e`'s verified replay cache: a replay is a test script written only after a passing check, it runs before any manual drive, and a stale replay is reported instead of letting an agent redo it. Keep them when syncing those skills. Actual model/effort availability is still checked by each running host. No global host model or permission setting is changed by setup.

`references/runtime.md` holds the shared contract. The Codex and Claude adapters hold only native tool and goal differences. Every skill reads the shared contract; parent agents relay the same resolved policy to workers. Canonical project skills remain in `.agents/skills`, with individual non-overwriting `.claude/skills` links for discovery. Existing projects are not rewritten by installation.

`bin/transcripts.mjs` is a local addition with no upstream counterpart. `recall`, `correct` and `automate-me` list prior sessions through it instead of describing transcript paths in prose, and it enforces the shared runtime's cwd and time restriction before any content is read. Claude sessions come only from the project directory Claude Code derives from each requested cwd, and a session counts only if it recorded that cwd, because distinct paths can share a directory name and a session moved from another directory keeps its earlier cwd. Codex rollouts are opened only when modified inside the window, and only for their first `session_meta` record. The Claude directory rule was read from Claude Code 2.1.302 and checked against every existing project directory on the maintainer's machine; upstream's harness note (cursor/plugins#637) names only `/` and `.`, which misses paths with spaces, underscores or non-ASCII characters and those longer than 200 characters. `scripts/transcripts.test.mjs` covers both hosts with a temporary home.

Benny remains dormant. Its copied runtime entry discovers this shared contract instead of maintaining a duplicated adapter. Installing the package does not arm messages, remote writes, webhooks, goals, or scheduled runs.

## Upstream sync

`node scripts/check-upstream.mjs` reports whether upstream moved past the pin and which files changed; it reads through `gh api` only. Merge each changed file by its history in this fork, never by copying the upstream directory:

- A file this fork adapted: take upstream's intent and keep every adaptation this guide records; where upstream's wording is Cursor-specific, keep the fork's.
- A new upstream file: adapt it as earlier syncs did, with local frontmatter, the runtime-contract line, and the fork's host primitives.
- A file this fork never changed: apply the change, then check it against the decisions below. The 0.15.25 sync rewrote upstream's new fast-mode sentence in two otherwise untouched forensics playbooks.
- A file this fork deleted, such as `.cursor-plugin/plugin.json`: keep it deleted unless the change removes the recorded reason.

The [fork guards](./docs/ci.md#fork-guards) reject the denylisted Cursor primitives and require each local decision listed in `REQUIRED` in `scripts/check-fork.mjs`, by file and anchor sentence. A decision this guide records without such a rule is guarded only by reading, so read every change against the guide. When a sync changes a guarded decision on purpose, update its section here and its rule in the same commit. When `comparisonMayBeTruncated` is true, the file list is incomplete; sync through an intermediate upstream commit. Finish a sync by moving `UPSTREAM.json` and the first line of this guide to the new commit, adding a paragraph below that names what was taken, kept, and skipped, running the [verification](#verification) checks, and refreshing the installations with the commands under [T3 Code overlay](#t3-code-overlay).

The orch store lock carries a local fix for three races that upstream still has at `e5136d82`: a writer killed between the exclusive open and its pid write left an empty lock that only `--force` could pass, two writers that saw the same dead holder could both take the lock, and a release could unlink the lock a `--force` writer had just put in its place. `acquireLock` now writes the pid to a private file and hard-links it into place, falling back to the exclusive open where hard links are unsupported. Every read-then-unlink of the lock, in a takeover or a release, runs behind a `.orch.lock.takeover` claim, and a takeover re-reads the holder before it unlinks. A writer that meets a live claim is refused with `is being released or replaced; retry`; a release that meets one retries every 10 ms, so `close` waits while a live claimant, even a stopped one, holds it. ## T3 Code overlay

The 0.15.25-shared.5 review fix preserves the complete parent model selection for inherited T3 roles. The resolver omits `target` and reports requested effort as unsent because T3 replaces supplied options and does not expose the parent's complete selection in its catalog. Explicit targets retain their supported effort mapping. Version following requires the current server-filtered catalog; older T3 builds affected by hidden-model catalog omissions must be upgraded or use an explicitly approved exact target.

T3 Code runs Codex or Claude Code underneath, so it is an overlay on the selected host adapter, not a fourth host. `references/t3-runtime.md` applies only when the session exposes T3's `orchestrator_capabilities` and `delegate_task` tools; an inherited `T3CODE_CLI_PATH` alone does not activate it. A T3 change therefore never alters native Codex or Claude sessions, and their overrides never reach T3. `scripts/config.test.mjs` covers that isolation. `bin/watch-pr.mjs` gains a local `--once` flag for T3 babysit rounds: it classifies once, never sleeps or retries, and ends a wait as `TIMEOUT`; `watch-pr/once.test.ts` covers it, and for it the upstream watch-pr tests only gain the `once: false` default. chhoumann/t3-pstack, a T3 port of the pstack-claude lineage, informed the tool mapping; none of its files are vendored.

## watch-pr merge gates

`watch-pr` fails closed on the merge gates GitHub enforces, a local port of michael-denyer/pstack-claude (MIT) [#95](https://github.com/michael-denyer/pstack-claude/pull/95), [#223](https://github.com/michael-denyer/pstack-claude/pull/223) and [#245](https://github.com/michael-denyer/pstack-claude/pull/245), with [#124](https://github.com/michael-denyer/pstack-claude/pull/124)'s `satisfies never` check on the merge-gate hint. `LICENSE` carries that project's copyright line. Upstream reported `READY` for PRs GitHub would not merge: it gated only closed, draft and `CHANGES_REQUESTED` PRs, accepted `BLOCKED` beside a passing rollup, and passed unknown mergeability. `READY` now requires `mergeable: MERGEABLE` and a settled merge state. `mergeStateStatus: BEHIND` stops at the `behind-base` merge gate without waiting for checks, since updating restarts them. `reviewDecision: REVIEW_REQUIRED` stops at `review-required`, and `BLOCKED` beside a passing rollup at `merge-blocked`; both wait for pending checks first, as `draft-pr` does. All three exit 6 in single, `--stack` and `--queued-stack` mode. Unknown mergeability is a `mergeability-unknown` wait, so `--once` ends it as `TIMEOUT`. PR facts come from one GraphQL query that reads the base branch's current commit, `baseRef.target.oid`, instead of `gh pr view`, whose `baseRefOid` is the commit the PR recorded. Each open snapshot reads the facts again after its checks and retries as `snapshot-changed` when one moved, except mergeability GitHub computed between the reads. An open PR without a head or base commit fails closed, and `READY`'s proof names both. Babysit treats `review-required` as the owner-approval wait, `behind-base` as a rebase to report and `merge-blocked` as a rule to name. Shipping does step 4's move for `behind-base` and stops at the other two. `watch-pr/merge-gates.test.ts` covers each gate and failed on the previous source; upstream's watch-pr tests change only where they pinned one facts read per snapshot, the `gh pr view` response, or the waiting decision's `pending` field. Keep these edits when a sync touches watch-pr.

Two pstack-claude changes are not taken. Its shared `WatchDeadline` (#124) changes exit codes at the deadline edge and is independent of these gates. Its `ci-none` verdict ([#153](https://github.com/michael-denyer/pstack-claude/pull/153)) is not ported, so a PR in a repository with no checks configured stays fail-closed: `gh pr checks` exits 1 with "no checks reported", the head has no rollup, and the watcher ends at `BLOCKER status-query` (exit 7, `checks-unavailable`) at once under `--once` or after `--max-query-errors` reads. It is never `READY`, and a person confirms such a PR.

## Verification

Run the offline runtime checks for configuration, guard, receipt, process and host-acceptance behavior:

```sh
bash scripts/check.sh runtime
```

For all CI checks, including strict TypeScript checks, Bun tests and reproducible bundle verification, follow [Run the CI checks locally](./docs/ci.md). The same entrypoint runs in GitHub Actions without vendor credentials.

The CLI tests use real Git checkouts and subprocesses with vendor stand-ins, including staged/committed read-only violations, misleading verdicts, timeout and cancellation. Vendor acceptance pins the fixture's test contents and checks the worker's successful test receipt against its final source before independently rerunning it. The shared verification runner gives each command a fresh Python bytecode-cache prefix and disables cache writes; `-B` alone can still load stale bytecode after an equal-size edit in the same second. A worker receipt is not sufficient without that independent run. Importing the test, rewriting it, or reusing a receipt from older code cannot satisfy the full acceptance gate.

Run `scripts/xagent-e2e.sh` after changing `bin/xagent*` or upgrading an agent CLI; it calls every vendor. Run `python3 scripts/pstack-host-e2e.py <new-run-dir>` after changing cross-agent routing: actual Claude and Codex hosts run swarm, then interrogate, through their current shared policy on synthetic fixtures. The host harness accepts a run only on evidence the host cannot write, such as xagent receipts, the host's own logs, snapshots the snapshot tool printed, and its own independent tests, because the host's success report is the thing under test. Its acceptance rules live in the script's module docstring, beside the code and tests that enforce them, so change them there. Neither harness changes preferences. Both bound the outer host process with `timeout` and a kill-after limit, and a verification timeout is a failed check with exit code 124.

The runtime checks start with `scripts/check-fork.mjs`, which validates the manifests, all SKILL.md and agent frontmatter, each skill's link to the shared runtime contract, local links, a denylist of the Cursor-only wording this guide replaces, and the files and anchor sentences of the local decisions it requires; see [Fork guards](./docs/ci.md#fork-guards). Use a fresh Codex app-server skills/list and Claude `plugin details` to verify inventory; a static validator alone is not a discovery or behavioral test.

Rebuild the `orch` and `watch-pr` bundles with `python3 scripts/build-runtime.py` when their sources, dependencies or builder change. Use the Bun version in `.bun-version` and locked development dependencies. `python3 scripts/build-runtime.py --check` compares a temporary build with the working tree without writing artifacts. Node runtime helpers never download dependencies.

See the task's shared-installation report for actual dated commands/results and any remaining gaps. No overnight, real PR queue, remote runner, or Slack workflow is implied by local package validation.
