## Maintained source

The repository `mtmtian/pstack-remix` is maintained as one checkout per machine for both hosts. `.codex-plugin/plugin.json` preserves the installed Codex name; `.claude-plugin/plugin.json` exposes the Claude name `pstack`. The repository includes native marketplace manifests for both hosts, named `pstack-local`. Existing Codex `personal` registrations may keep pointing at the same checkout. Both consume the same 55 skills, 23 playbooks, 2 agent files, and runtime helpers. Host caches are generated installation artifacts, never edit targets.

Shared preferences live at `~/.config/pstack/config.json`. `bin/config.mjs` supplies read-only resolution, idempotent initialization/legacy import, host-scoped updates, null-to-remove overrides, validation, locking, and atomic writes. A concrete model ID cannot be stored in the common policy. An `xagent:<agent>` entry can, because `bin/xagent` dispatches it to the named local agent CLI the same way from either host; so can `xagent:<agent>/<model>`, whose model goes only to that CLI's own model flag. `bin/xagent --effort` maps the worker's effort to each CLI's own effort flag, and the receipt records the requested model and effort. The `xagent` skill, its allowlist, and the pi guard are local additions with no upstream counterpart; `scripts/xagent-e2e.sh` is their behavioral test. Replays in `create-verification-skill` and `maintain-verification-skill` are also local additions, adapted from tester.army `e2e`'s verified replay cache: a replay is a test script written only after a passing check, it runs before any manual drive, and a stale replay is reported instead of letting an agent redo it. Keep them when syncing those skills. Actual model/effort availability is still checked by each running host. No global host model or permission setting is changed by setup.

`references/runtime.md` holds the shared contract. The Codex and Claude adapters hold only native tool and goal differences. Every skill reads the shared contract; parent agents relay the same resolved policy to workers. Canonical project skills remain in `.agents/skills`, with individual non-overwriting `.claude/skills` links for discovery. Existing projects are not rewritten by installation.

Benny remains dormant. Its copied runtime entry discovers this shared contract instead of maintaining a duplicated adapter. Installing the package does not arm messages, remote writes, webhooks, goals, or scheduled runs.

## Upstream sync

`node scripts/check-upstream.mjs` reports whether upstream moved past the pin and which files changed; it reads through `gh api` only. Merge each changed file by its history in this fork, never by copying the upstream directory:

- A file this fork adapted: take upstream's intent and keep every adaptation this guide records; where upstream's wording is Cursor-specific, keep the fork's.
- A new upstream file: adapt it as earlier syncs did, with local frontmatter, the runtime-contract line, and the fork's host primitives.
- A file this fork never changed: apply the change, then check it against the decisions below. The 0.15.25 sync rewrote upstream's new fast-mode sentence in two otherwise untouched forensics playbooks.
- A file this fork deleted, such as `.cursor-plugin/plugin.json`: keep it deleted unless the change removes the recorded reason.

The fork guards catch only the denylisted primitives, so read every change against the decisions in this guide. When `comparisonMayBeTruncated` is true, the file list is incomplete; sync through an intermediate upstream commit. Finish a sync by moving `UPSTREAM.json` and the first line of this guide to the new commit, adding a paragraph below that names what was taken, kept, and skipped, running the [verification](#verification) checks, and refreshing the installations as described under Antigravity integration.

The orch store lock carries a local fix for three races that upstream still has at `e5136d82`: a writer killed between the exclusive open and its pid write left an empty lock that only `--force` could pass, two writers that saw the same dead holder could both take the lock, and a release could unlink the lock a `--force` writer had just put in its place. `acquireLock` now writes the pid to a private file and hard-links it into place, falling back to the exclusive open where hard links are unsupported. Every read-then-unlink of the lock, in a takeover or a release, runs behind a `.orch.lock.takeover` claim, and a takeover re-reads the holder before it unlinks. A writer that meets a live claim is refused with `is being released or replaced; retry`; a release that meets one retries every 10 ms, so `close` waits while a live claimant, even a stopped one, holds it. The fix and its multi-process race tests are adapted from michael-denyer/pstack-claude #219 (`eef8f7c6`) and #238 (`de804764`), MIT, Copyright (c) 2026 Michael Denyer, whose notice is added to `LICENSE`. That fork's TLA+ model and its retry when a lock vanishes before its holder is read are not taken. The lock lives in `skills/poteto-mode/scripts/orch/lock.ts`, with `UserError` and `errorCode` in `orch/errors.ts`, because this fork replaced upstream's lock wholesale and `store.ts` was already past 1,000 lines; its race tests live in `orch/lock.test.ts`, sharing `orch/store.test-helper.ts` with `orch.test.ts`. Each acquire also removes the private pid files and staged claims that a writer killed mid-claim leaves behind, judged by the pid in their names, which the kill-at-every-step test now checks. The frontier code stays in `store.ts` even though it is large, so upstream's edits there still merge file by file. Its GitHub remote parsing is `skills/poteto-mode/scripts/github-remote.ts`, moved out of upstream's `watch-pr/github.ts` so `orch` and `watch-pr` share one parser.

## T3 Code overlay

T3 Code runs Codex or Claude Code underneath, so it is an overlay on the selected host adapter, not a fourth host. `references/t3-runtime.md` applies only when the session exposes T3's `orchestrator_capabilities` and `delegate_task` tools; an inherited `T3CODE_CLI_PATH` alone does not activate it. It replaces model resolution, delegation, scheduling, and PR watching with `delegate_task`, `task_status`, `schedule_task`, and `watch_pull_request`. Skills, playbooks, authorization, evidence rules, and `bin/xagent` stay shared, so agents T3 does not list, such as Gemini, and every `required_panel_members` entry still run through xagent.

`show --host t3` returns common policy plus an optional `hosts.t3` section and never reads `hosts.codex` or `hosts.claude`. That section also accepts T3 targets `<providerInstanceId>/<modelId>`, validated by `bin/config.mjs`; files without it remain valid, and older helpers ignore it. A T3 change therefore never alters native Codex or Claude sessions, and their overrides never reach T3. `scripts/config.test.mjs` covers that isolation. `bin/watch-pr.mjs` gains a local `--once` flag for T3 babysit rounds: it classifies once, never sleeps or retries, and ends a wait as `TIMEOUT`; `watch-pr/once.test.ts` covers it, and for it the upstream watch-pr tests only gain the `once: false` default. chhoumann/t3-pstack, a T3 port of the pstack-claude lineage, informed the tool mapping; none of its files are vendored.

After maintained-source changes, refresh the existing installations with `agy plugin install <source>`, `codex plugin add pstack-codex@personal` for this machine's existing Codex ID, and `claude plugin update pstack@pstack-local`. Do not flatten pstack skills into shared standalone names or restore retired paseo aliases.

## watch-pr merge gates

`watch-pr` fails closed on the merge gates GitHub enforces, a local port of michael-denyer/pstack-claude (MIT) [#95](https://github.com/michael-denyer/pstack-claude/pull/95), [#223](https://github.com/michael-denyer/pstack-claude/pull/223) and [#245](https://github.com/michael-denyer/pstack-claude/pull/245), with [#124](https://github.com/michael-denyer/pstack-claude/pull/124)'s `satisfies never` check on the merge-gate hint. `LICENSE` carries that project's copyright line. Upstream reported `READY` for PRs GitHub would not merge: it gated only closed, draft and `CHANGES_REQUESTED` PRs, accepted `BLOCKED` beside a passing rollup, and passed unknown mergeability. `READY` now requires `mergeable: MERGEABLE` and a settled merge state. `mergeStateStatus: BEHIND` stops at the `behind-base` merge gate without waiting for checks, since updating restarts them. `reviewDecision: REVIEW_REQUIRED` stops at `review-required`, and `BLOCKED` beside a passing rollup at `merge-blocked`; both wait for pending checks first, as `draft-pr` does. All three exit 6 in single, `--stack` and `--queued-stack` mode. Unknown mergeability is a `mergeability-unknown` wait, so `--once` ends it as `TIMEOUT`. PR facts come from one GraphQL query that reads the base branch's current commit, `baseRef.target.oid`, instead of `gh pr view`, whose `baseRefOid` is the commit the PR recorded. Each open snapshot reads the facts again after its checks and retries as `snapshot-changed` when one moved, except mergeability GitHub computed between the reads. An open PR without a head or base commit fails closed, and `READY`'s proof names both. Babysit treats `review-required` as the owner-approval wait, `behind-base` as a rebase to report and `merge-blocked` as a rule to name. Shipping does step 4's move for `behind-base` and stops at the other two. `watch-pr/merge-gates.test.ts` covers each gate and failed on the previous source; upstream's watch-pr tests change only where they pinned one facts read per snapshot, the `gh pr view` response, or the waiting decision's `pending` field. Keep these edits when a sync touches watch-pr.

Two pstack-claude changes are not taken. Its shared `WatchDeadline` (#124) changes exit codes at the deadline edge and is independent of these gates. Its `ci-none` verdict ([#153](https://github.com/michael-denyer/pstack-claude/pull/153)) is not ported, so a PR in a repository with no checks configured stays fail-closed: `gh pr checks` exits 1 with "no checks reported", the head has no rollup, and the watcher ends at `BLOCKER status-query` (exit 7, `checks-unavailable`) at once under `--once` or after `--max-query-errors` reads. It is never `READY`, and a person confirms such a PR.

## Verification

Run the offline runtime checks for configuration, guard, receipt, process and host-acceptance behavior:

```sh
bash scripts/check.sh runtime
```

For all CI checks, including strict TypeScript checks, Bun tests and reproducible bundle verification, follow [Run the CI checks locally](./docs/ci.md). The same entrypoint runs in GitHub Actions without vendor credentials.

The CLI tests use real Git checkouts and subprocesses with vendor stand-ins, including staged/committed read-only violations, misleading verdicts, timeout and cancellation. Vendor acceptance pins the fixture's test contents and checks the worker's successful test receipt against its final source before independently rerunning it. The shared verification runner gives each command a fresh Python bytecode-cache prefix and disables cache writes; `-B` alone can still load stale bytecode after an equal-size edit in the same second. A worker receipt is not sufficient without that independent run. Importing the test, rewriting it, or reusing a receipt from older code cannot satisfy the full acceptance gate.

Run `scripts/xagent-e2e.sh` after changing `bin/xagent*` or upgrading an agent CLI; it calls every vendor. Run `python3 scripts/pstack-host-e2e.py <new-run-dir>` for actual Claude and Codex hosts executing swarm then interrogate through their current shared policy on synthetic fixtures. It records source hashes, policy, worker receipts and independent tests, and checks that the parent verified the final source and that each configured reviewer saw it in a separate worktree. It checks `xagent:` entries through their receipts, counting a `meta.json` as an xagent attempt when either marker `bin/xagent` creates first (`prompt.md`, `agent.log`) sits beside it, so a broken one still fails, keyed by mode, agent and model, and listing any other `meta.json` under the evidence directory as ignored, and native entries through the host's own log, parsed by `scripts/e2e-native-evidence.py`: Claude's stream-json Agent calls and their resolved model, or Codex's persisted session rollouts (the Codex host therefore runs without `--ephemeral`). A native dispatch's checkout comes from its subagent's own tool calls: the Claude events whose `parent_tool_use_id` is its Agent call, or the Codex child rollout (whose task payload is encrypted). Those calls must use exactly one checkout under the run other than the parent, and it must be a linked worktree at the fixture base. The dispatch writes when it edited that checkout with its host's file-edit tool and the edit succeeded (Claude `Write`/`Edit` with a successful tool result, a completed Codex `FileChange`), and reviews when it edited nothing there and the checkout holds the final `stats.py`. A native review must also bracket its work, as xagent's `snapshot_before` and `snapshot_after` do: its subagent's own first and last shell commands in that worktree are `python3 -B scripts/e2e-snapshot.py <worktree>`, every other shell command there falls between them, and every printed snapshot (which leaves ignored test receipts and caches out) matches the worktree's state when the run ends. A shell edit during a review, before it, or after it therefore stops it counting. Shell edits are not writer evidence, so a writer that edits only through the shell cannot fill the writer slot. When the effective policy sets `reasoning_effort`, a worker fills a role only if its xagent receipt, Claude Agent call or Codex `spawn_agent` records an effort level; the level itself may differ, since poteto-mode adjusts it per task. Each checkout belongs to one owner, a worker (kind, agent and model) in one mode, so an xagent retry or a native writer's follow-up fix may reuse its worktree; and each configured writer or reviewer slot needs an attempt in a checkout no other slot used, so two reviews in one worktree count once. A missing log or a dispatch that used no path is reported as a gap and fails the check. It never changes preferences. Each worker attempt is limited to xagent's default 900 seconds with one retry, not doubled. Both live harnesses use `timeout` with a kill-after limit for the outer host process; host workflows default to 6 attempts × (900-second limit + xagent's termination grace + 30 seconds of start-up and snapshots) + 600 seconds of host work + both final checks, so the writer, review and post-fix re-review rounds can each retry, configurable with `--host-timeout`. Verification commands use `scripts/e2e-process.py` with a 30-second default deadline, process-group termination and bounded output collection; the host harness exposes `--check-timeout`. A verification timeout remains a failed check with logs and exit code 124.

The runtime checks start with `scripts/check-fork.mjs`, which validates the manifests, all SKILL.md and agent frontmatter, each skill's link to the shared runtime contract, local links, and a denylist of the Cursor-only wording this guide replaces; see [Fork guards](./docs/ci.md#fork-guards). Use a fresh Codex app-server skills/list and Claude `plugin details` to verify inventory; a static validator alone is not a discovery or behavioral test.

Rebuild the `orch` and `watch-pr` bundles with `python3 scripts/build-runtime.py` when their sources, dependencies or builder change. Use the Bun version in `.bun-version` and locked development dependencies. `python3 scripts/build-runtime.py --check` compares a temporary build with the working tree without writing artifacts. Node runtime helpers never download dependencies.

See the task's shared-installation report for actual dated commands/results and any remaining gaps. No overnight, real PR queue, remote runner, or Slack workflow is implied by local package validation.
