# Claude Code adapter

Read [the shared runtime](./runtime.md) first. This file defines only Claude Code behavior. Use the current tool schemas even when an installed CLI version differs from the version used to validate this package.

- Entry points are `/pstack:poteto-mode`, `/pstack:setup-pstack`, and other `/pstack:<skill>` names. The same `skills/` files are used by Codex. Do not call `$pstack-codex:*` as Claude commands.
- Resolve preferences with `node <plugin-root>/bin/config.mjs show --host claude`. Default to the main conversation's model. For shared agents, frontmatter `model: inherit` preserves inheritance. Use a concrete per-call model only when the actual Agent schema and account support it. Claude aliases/model IDs are not Cursor slugs or Codex IDs; GPT/Grok models require a separately configured, authorized provider/bridge and must not be assumed available; `xagent:<agent>` policy entries are that bridge for local agent CLIs (see the shared runtime). Use a supported separate effort control, or inherit session effort when none is exposed.
- Use Claude's actual `Agent` tool with its supported `subagent_type`; available types can include `general-purpose`, `Explore`, `pstack:poteto-agent`, and `pstack:comment-sicko`. The two plugin agent files are native Claude definitions. The comment reviewer has only Read/Grep/Glob and returns proposals, not edits. The general workflow agent reads the same poteto-mode and shared configuration as the parent.
- Respect the current nesting and concurrency limits. Select background execution only when the tool supports it. Track returned IDs and actual completion notifications/output, and inspect artifacts before accepting results. Do not call Codex `collaboration.*`, assume an empty output means success, or interrupt merely to tidy the agent list. If a role cannot delegate, it performs feasible scoped work and returns evidence.
- In a one-shot/headless parent (`claude -p`), join external workers before the final reply. Run parallel xagent commands with `&` inside one foreground Bash call and `wait` for every returned PID; give that call a timeout longer than the worker deadlines and termination grace. Use a native blocking wait only when its current schema actually provides one. Ending with a promise to receive background notifications can exit the parent and cancel those workers; a Monitor or shell sentinel is not a substitute for collecting their terminal results.
- For isolated writers, use an actual worktree at the intended base SHA. Do not assume the default branch used by a host-created worktree matches the parent's HEAD. Verify it.
- Claude's native `/goal` is a session feature with its own evaluator and lifecycle. Check for an existing goal before replacing it. A skill invocation does not activate one. On explicit user intent, use the native command/control actually exposed in that session; if it requires user command entry, explain that exact prerequisite and continue feasible work. Do not invent `create_goal`, `get_goal`, or `update_goal` tools. Surface the completion evidence for the evaluator instead of pretending to set Codex-style statuses. On stop/pause follow the host's real goal clearing behavior and preserve a checkpoint.
- `/loop` and Cron tools, when present, handle separately requested session scheduling. Verify the actual job ID and cadence. A goal is not a schedule; a background Bash process is not a durable automation. Do not promise operation after session exit or restart without testing that exact path.
- Project/user instructions come from the current Claude environment. Use supported history/resume tools or narrowly scoped local session records; do not invoke Codex task APIs or assume Cursor transcript paths.

Official references: [plugins](https://code.claude.com/docs/en/plugins), [subagents](https://code.claude.com/docs/en/sub-agents), [goal](https://code.claude.com/docs/en/goal), [scheduling](https://code.claude.com/docs/en/scheduled-tasks).
