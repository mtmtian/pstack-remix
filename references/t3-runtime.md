# T3 Code overlay

Read [the shared runtime](./runtime.md) and the Codex or Claude Code adapter first. T3 Code runs one of those hosts underneath, so files, shell, skill entry points, goals, and project instructions still follow that host adapter. This overlay replaces only four things: model resolution, delegation, scheduling, and PR watching.

## When it applies

Apply it only when the current session exposes T3's orchestration tools `orchestrator_capabilities` and `delegate_task`, under any MCP prefix such as `mcp__t3-code__delegate_task`. An environment variable such as `T3CODE_CLI_PATH` is not enough, because processes started from a T3 thread inherit it without the tools. Without both tools, ignore this file and use the host adapter alone. A T3 child that exposes the tools follows this overlay for nested work inside its brief and limits.

## Resolve policy

Run `node <plugin-root>/bin/config.mjs show --host t3`. The T3 view is common policy plus the optional `hosts.t3` section. It never reads `hosts.codex` or `hosts.claude`, whichever host runs the thread, because those hold host-native IDs. Update it with `update --host t3`, through [setup](../skills/setup-pstack/SKILL.md). A difficulty rule shared with the native hosts does not share their model assignments: direct Claude Code still reads `hosts.claude`, and an unconfigured role there inherits its main conversation.

A T3 entry is `inherit-parent`, `auto`, `xagent:<agent>[/<model>]`, or a T3 target `<providerInstanceId>/<modelId>`. Split a target at the first `/`; model IDs may contain more slashes. An entry that starts with `xagent:` is never a T3 target, even with a model.

T3 roles also accept `{"candidates":["codex/gpt-sol@latest","claudeAgent/claude-opus@latest"]}`. Candidates contain exactly one target per provider. The helper selects the parent provider when present, otherwise the first candidate. `--provider <id>` selects another configured candidate for a reason stated in the brief. This produces one worker, not a panel or a fallback chain. Availability is checked after selection; a failed selection stays failed. Panels remain ordered arrays of independent seats.

An explicit family selector ends in `@latest`, such as `claudeAgent/claude-opus@latest` or `codex/gpt-sol@latest`. The helper chooses the highest numeric major/minor release in that provider's current catalog. Supported families are Claude opus/fable/sonnet/haiku and GPT sol/astra/luna. Only canonical `claude-<family>-<major>[-<minor>]` and `gpt-<major>[.<minor>]-<family>` IDs match, with one to three digits per version component. Routed/custom aliases, previews, dated snapshots and context variants do not match. Unknown naming schemes require an exact ID or a resolver update, not a guess. It never switches provider or family, and unsupported effort on the newest release does not select an older release. Exact targets stay pinned.

Call `orchestrator_capabilities` before the first dispatch of a task and save its raw structured result, including `providers`, `inheritedProviderInstanceId`, `inheritedModel` and, from T3 0.1.1, `inheritedOptions`, to a task-local JSON file. Use this task's catalog, not a saved catalog from setup or another thread. From T3 0.1.2 the result is a short list: every current Codex, Claude, Muse and Grok model, the user's favorite and custom models, the caller's own model, and the first eight current models of other providers, with each provider's `omittedModels` counting the rest. When the preview says a target is not among the listed models, call `orchestrator_capabilities` again with `search` set to that model, such as `sonnet 4.6`, save that result too, and pass it as another `--catalog` after the first. Every result must come from this thread. A hidden model never appears, even in a search. On a provider whose list is partial, `@latest` fails because it cannot see every release; pin an exact ID there. Preview the role or whole panel through the shared helper:

Version following requires a T3 catalog that respects the environment's hidden-model preferences. Current T3 filters those models server-side; older builds affected by [T3 #15716](https://github.com/pingdotgg/t3code/issues/15716) did not. If a hidden model is still advertised, upgrade T3 or use an explicitly approved exact target before dispatch. Do not read another client's picker settings as an environment-wide policy.

```sh
node <plugin-root>/bin/config.mjs resolve --host t3 --role 'feature' --catalog <catalog.json>
node <plugin-root>/bin/config.mjs resolve --host t3 --role 'feature' --provider claudeAgent --catalog <catalog.json>
node <plugin-root>/bin/config.mjs resolve --host t3 --panel 'interrogate reviewers' --catalog <catalog.json>
node <plugin-root>/bin/config.mjs resolve --host t3 --role 'verification workers' --checked inherit-parent --catalog <catalog.json>
node <plugin-root>/bin/config.mjs resolve --host t3 --role 'feature' --catalog <catalog.json> --catalog <search.json>
```

Use the role the playbook requests. For a per-job effort adjustment, add `--effort <level>` after applying poteto-mode's rule. The helper reads the same effective policy as `show`; it writes nothing and starts no task. `selection.defaulted` means that role or panel was absent and used the shared inherited default. It checks each T3 provider, child capability, cross-provider capability, exact model and effort choice. An invalid member fails the whole preview before dispatch; report the named target and constraints. Do not substitute another model, provider, or `xagent:<agent>` unless the user says so.

A step that checks other work resolves with `--checked <entry or model>`, naming what produced that work: `inherit-parent` when the parent wrote it, the writer's resolved `<providerInstanceId>/<modelId>`, or `xagent:<agent>/<model>`. Every worker reports `family`, read only from the last segment of its model ID: canonical `claude-`, `gpt-`, `gemini-` and `grok-` IDs name a family, anything else is unknown. A provider name never decides it, because one provider can route other vendors' models. A candidate role then takes the first candidate, the parent provider's first, whose known family differs from the checked work's (`selection.strategy: cross-family`). When none does, or either family is unknown, the default selection stands with a warning: label that review same-family, or say it is not cross-family evidence. `verification workers` fails without `--checked` unless `--provider` names a candidate for a reason the brief states. For a pool such as `arena cross-judge pool`, resolve the panel with `--checked inherit-parent` and choose a seat without a family warning. An `xagent:<agent>` entry without a model has an unknown family; pin its model where family evidence matters.

For candidate roles, `selection.strategy` and `selection.entry` explain the chosen candidate. Each worker's `entry` retains the configured selector; `resolved` and `target` contain the concrete model. Dispatch only `target`, never an `@latest` string or candidates object. Save and reuse this task's resolved model IDs, including for later rounds, so a catalog change cannot silently change a running task. Start the next task with a fresh catalog. The [routing examples](../docs/t3-model-routing.md) show phase changes, upgrades and native-host differences.

| Entry | `delegate_task` target |
| --- | --- |
| `inherit-parent`, `auto` | Omit `target` (`null` in the preview) to preserve the parent's complete model selection and options. When effort is requested and the catalog lists `inheritedOptions` (T3 0.1.1 and later), the preview's `target` names the parent's own provider and model with only the effort option; T3 overrides that one value and keeps every other parent option, so send it as previewed. When the parent model does not offer that effort, or the catalog has no `inheritedOptions` (T3 0.1.0, which replaced the whole option set), `target` stays `null` and the effort is reported unsent. `resolved` names the parent used for validation, not a replacement target. T3 has no automatic model router |
| `<providerInstanceId>/<modelId>` | Use that worker's exact previewed `target`, including its options |
| `xagent:<agent>[/<model>]` | The worker has `transport: xagent` and separate `agent`, `model`, `effort` and `warnings`; `effort` is already lowered to the agent's `xagent_effort_caps` entry, with a warning when it was. Run its entry through `bin/xagent` as the shared runtime specifies; never pass it to T3 as a model |

For explicit targets, the helper maps effort to the model's listed select control (`effort`, `reasoningEffort`, or `thinking`), without guessing from its provider name. It reads either catalog form, T3 0.1.0's `{type: "select", options}` or 0.1.2's `{values}`; a boolean option is never an effort control. An unsupported value is an error; if it was a per-job adjustment, the shared rule allows retrying the original policy value, with disclosure. A model with no effort control produces a warning and `effort.sent: null`; it runs with its runtime default, so do not claim that the requested effort was applied. An inherited target sends effort only as the table says. Never send an empty `options` (`[]` or `{}`): it clears the parent's inherited values. Report warnings. The preview adds no speed or service-tier option; do not add one unless the user asked. A preview proves selection only, not authentication or execution.

## Delegate

In a T3 session every pstack worker is an explicitly T3-owned child task, so it goes through `delegate_task`, including `inherit-parent` roles. T3 prefers native subagent tools for same-provider work only when they support the chosen model, and sends explicitly T3-owned child tasks through `delegate_task`; pstack workers take that path so the thread owns and shows each child, T3 isolates it in an application-owned worktree, and every provider leaves the same `taskId` receipt. Do not also use the host's native subagent tool for the same role. The host adapter's rule that a native agent definition owns its effort does not apply here: the resolved `hosts.t3` policy owns each child's model and effort.

| pstack action | On T3 |
| --- | --- |
| Start a worker | `delegate_task` with `mode: "async"`, `isolation: "worktree"`, the target above, a `title`, a `role` (`review` for reviewers and judges, `research` for explorers, `design` for architect and arena runners, `implementation` for writers, `test` for verification), and a `clientRequestId` such as `<skill>-<run>-r<round>-<member>`, stable across retries of that dispatch. Keep the returned `taskId` and `childThreadId`; do not create another task after a lost reply until that request has been recovered |
| Parallel workers | One `delegate_task` call per entry in the same response |
| Wait | End the turn. The child's completion wakes the thread. Call `task_status` only when this turn needs the result. Accept only `status: completed` with `workState: result_available` and a `summary` you have read. `working`, `waiting_for_children`, or `waitTimedOut` is not completion, nor is a non-null `pendingApproval` (T3 0.1.1 and later): the child waits on an approval, which grants this thread no approval authority. Read the child's fresh request with `t3_thread_read` and apply the host's approval rules, asking the user where they require it. A `failed` status also reports `result_available`; treat it as that entry's `DROPOUT` under the shared rules, since `canRunChildTask` does not prove the provider is authenticated |
| Fix round or follow-up | A new `delegate_task` with the original brief, every later directive, prior findings, responses, and unresolved objections, and a new `clientRequestId`. Never `t3_thread_send` to a `childThreadId` |
| Stop a worker | `task_cancel`, then `task_status` to confirm |
| `poteto-agent`, `comment-sicko` | Open the task with the absolute path of `agents/poteto-agent.md` or `agents/comment-sicko.md` and tell the child to read it first, as on Codex |

Every brief is standalone, because the child gets no parent history. It carries the shared runtime's fields: host, plugin root, configuration path, the resolved T3 policy snapshot, scope, and verification predicate.

T3 creates and owns the worktree when `isolation: "worktree"` is set; omitting it shares the parent's checkout. Use the application-owned worktree for both writers and reviewers, and do not also create a manual worktree for the same task. A child can inspect its cwd; the parent reads the actual `worktreePath` with `t3_thread_read`. Give the brief the expected base SHA and require the child to check it before editing or reviewing. Isolation starts from the parent's local commit and runs project setup; it does not copy uncommitted changes. Commit the needed input only when authorized, or supply a named patch/content snapshot and explicitly prepare it in the child's owned worktree. Verify the prepared source hash before accepting its result. A review must see the final candidate, not merely the parent's earlier HEAD.

`role: review` is a label, not a read-only sandbox. State the read-only boundary in the brief. Record HEAD and a working-tree baseline after setup/preparation and compare them after review; setup may already have produced ignored files. Run checks that write nothing where required, for example `python3 -B`, and keep receipts outside the reviewed files. Two attempts never share an owned checkout. A failed or cancelled attempt is not replaced while it still owns live work.

Keep the preview, dispatch response and terminal `task_status` together with the actual checkout, input/output hashes and verification output. Compare the requested target with the T3 task/run metadata; from T3 0.1.1, `task_status` also reports the child's stored `options`, which must hold every option the target sent. A mismatch is an unresolved execution failure. Record provider-observed model and effort separately when the runtime exposes them. Missing provider metadata is `unknown`, not evidence that the requested values ran. A completed summary cannot replace the parent's independent check of the artifact.

## Mixed panels

`xagent:<agent>` entries, including `required_panel_members`, still run through `bin/xagent` from the host shell. Their availability is checked by that CLI, not the T3 catalog, and they remain outside T3's child-task lifecycle. T3 may expose the same models directly or through another provider; consult the live catalog rather than a fixed vendor list. Do not automatically convert an xagent entry. Shared required members are still appended, so adding a T3 seat does not replace one. A panel worker's `auxiliary` is true only for a seat listed in shared `auxiliary_panel_members`: its unresolved outcome is a reported gap, while every other seat, and every role, blocks as the shared runtime specifies. Start T3 targets first so they run while the xagent commands block the shell call, then collect both. A family listed on both paths runs twice, as two independent attempts; a provider name alone does not identify the model family. Count and label them accurately. The final reply names the provider and model, or xagent agent, that ran each step, with its `taskId` or output directory.

## Schedules and PRs

- Recurrence the user asked for uses `schedule_task` bound to this thread instead of the host's `/loop` or Cron tools. Report the returned cadence and `nextRunAt`, and delete it with `delete_scheduled_task` when the loop ends.
- Babysit and Shipping never leave `bin/watch-pr.mjs` polling here. `check` keeps its single `--status-only` report. Every other mode adds `--once`: the helper classifies the current state once, without sleeping, retrying, or applying `--timeout`, and exits. Babysit acts on a terminal verdict (`READY`, a blocker, `COMPLETE`) or a queued-mode `WAITING` with reason `merge-queue` exactly as its playbook says. Shipping acts only on a blocker or on `COMPLETE` at the ceiling, so every `WAITING`, `merge-queue` included, is a wait there. Otherwise the run ends with its current `WAITING` reason followed by `TIMEOUT`: handle existing comments, call `watch_pull_request` on the current frontier PR, end the turn, and classify again with `--once` on the next wake. A query failure is the usual `BLOCKER` with exit 7; rerun on the next wake rather than waiting inside the helper. Call `unwatch_pull_request` before handing the PR back. Only the parent thread can watch. Register PRs this work creates or updates with `link_pull_request`.
- `t3_thread_launch` and `create_threads` create top-level threads. Use them only when the user asks for separate threads, never for pstack workers.
