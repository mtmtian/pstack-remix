### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn, resume, and account for workers with the host's collaboration tools and their actual schemas. Keep the program's state in `orchestrate/<project-slug>/`, in an explicit project or user state directory the operator selects, with `notes.md` as its tracker. Never write plugin installation files by assumption. Watch each PR with the host's PR and CI event subscriptions when it exposes them. Call no scripts, run no polling loops, and never relay messages or status between agents. If the operator explicitly asks for a durable program goal, record the program's done condition once through the selected host adapter. A goal records finite work; it does not schedule wakeups.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge, merging only under the run's merge authorization. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Give every writer an exclusive worktree or branch, and run it in the isolation the host actually provides unless the work needs this machine: a runtime check through the project's verification harness, local transcripts, a simulator, or auth that exists only here. Never claim isolation the host did not report. Set each worker's reasoning effort for the job, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers, or sooner at the host's nesting limit. Keep about ten workers in flight per coordinator, within the host's concurrency limit, and start the next one as each finishes instead of waiting on a whole batch.
- **Reuse a worker's built state,** such as its checkout, uncommitted changes, or a running process, by forking that worker where the host supports forks. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on the `verification workers` role, from a different available model family, or labeled as same-family independent review. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a check through the project's verification harness, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a merge or other external write the run's authorization does not cover, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
